推理服务监控

确保线上模型服务稳定、高效运行的关键环节。通过全方位指标收集与可视化，实现服务状态的可观测性。

核心监控指标

类别指标说明
性能吞吐量 (QPS)每秒处理的请求数
性能延迟 (Latency)P50, P95, P99 分位响应时间
资源GPU利用率显存占用、计算核心使用率
资源CPU/内存系统资源消耗
业务请求成功率HTTP 200 比例
业务模型输出分布预测分值、类别分布监控

监控系统组成

  • 数据采集: 在服务中埋点，使用Prometheus Client导出指标。
  • 存储与查询: Prometheus 作为时序数据库。
  • 可视化: Grafana 配置监控仪表盘。
  • 告警: AlertManager 根据规则发送通知。

模型版本管理

系统化地管理模型从开发到上线的生命周期，保证版本可追溯、可回滚、环境一致。

版本管理策略

  1. 语义化版本: 主版本.次版本.修订号 (如 2.1.0)
  2. 元数据存储: 模型文件、训练参数、评估指标、数据集快照。
  3. 版本标签: 生产版(prod)、测试版(staging)、开发版(dev)。

A/B 测试

科学评估新模型版本或算法策略在真实流量下的效果，为决策提供数据支持。

A/B测试流量调度架构

关键步骤

  • 流量分割: 基于用户ID、会话ID或随机数进行分流 (如 90% A, 10% B)。
  • 效果指标定义: 业务核心指标 (如点击率、转化率)、性能指标 (延迟)。
  • 统计显著性检验: 使用T-test或卡方检验判断差异是否显著。
  • 决策与全量: 优胜版本逐步放大流量直至全量。

模型热更新

在不中断服务的情况下，平滑地将线上模型替换为新版本，实现零停机部署。

热更新常见模式

  1. 影子模式: 新模型并行推理但不返回结果，用于验证正确性与性能。
  2. 蓝绿部署: 准备两套完全独立的环境，通过切换流量实现瞬间切换。
  3. 金丝雀发布: 先向小部分流量开放新模型，验证无误后逐步扩大范围。

技术实现要点

  • 模型加载隔离: 新模型加载到内存后再切换推理指针，避免加载阻塞请求。
  • 内存管理: 旧模型版本引用计数归零后安全释放GPU显存。
  • 回滚机制: 监控新模型异常时，自动快速切回上一稳定版本。
# 简化的热更新管理器伪代码
class ModelHotSwapper:
    def __init__(self, model_path):
        self.current_model = load_model(model_path)
        self.new_model = None

    def load_new_version(self, new_model_path):
        # 后台加载新模型，不影响当前服务
        self.new_model = load_model(new_model_path)
        warm_up(self.new_model) # 预热

    def swap(self):
        if self.new_model is not None:
            old_model = self.current_model
            self.current_model = self.new_model # 原子切换
            self.new_model = None
            schedule_gc(old_model) # 异步释放旧模型
            log("模型热更新完成")
